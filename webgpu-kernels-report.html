WebGPU Kernels: What They Are, and What You Can Actually Build With Them

1. The one-sentence version

Hugging Face published 207 hand-optimised GPU programs that run inside a web browser, put each one on the Hub as its own versioned repository, and shipped a small JavaScript library that downloads one and turns it into a normal async function you call with typed arrays. You get GPU-speed maths in a web page without writing a single line of shader code, and without sending any data to a server.

Everything is Apache-2.0 licensed. The library is @huggingface/kernels on npm. The kernels live at huggingface.co/webgpu-kernels. The authors are Nico Martin and Joshua Lochner (Xenova) on Hugging Face's WebAI team.

2. An operation is the recipe; a kernel is the recipe cooked for one kitchen

This is the distinction the whole release rests on, so it is worth getting right before anything else.

A machine learning model, once you strip away the framework, is a graph of small mathematical steps. Each step is an operation. An operation says what should happen and nothing about how. Addition is an operation: it takes a tensor A and a tensor B, and produces C = A + B. That description is hardware-free. It is true on a phone, a laptop, and a data-centre card.

A kernel is one implementation of that operation for one kind of hardware. The same addition needs different code depending on where it runs. On an NVIDIA card you would write a CUDA kernel. On Apple silicon, a Metal kernel. In a browser you use the WebGPU API, and the language you write in is WGSL — the WebGPU Shading Language. Same recipe, different kitchen, different code.

Analogy

The operation is "make a béchamel". The kernel is the version of that recipe written for your stove — gas, induction, or a camping burner. The dish is identical. The instructions are not, and the difference between a good set of instructions and a bad one is minutes of your life.

Why does that difference matter so much? Because a model run is thousands of these steps in sequence. If each individual operation is 2x faster, the whole model is roughly 2x faster. Kernels are the floor of the stack. Nothing built on top of them — no runtime, no clever scheduler — can be faster than the operations it dispatches. That is the argument for starting here rather than higher up.

3. Why they ship templates instead of finished shaders

Here is the part that surprised me, and it is the most interesting engineering decision in the release.

The repositories do not contain .wgsl files. They contain .wgsl.jinja files — Jinja templates, the same templating language Python people use for HTML. The finished shader is not written by a human and shipped. It is generated in your browser, at load time, for your specific GPU and your specific input shapes.

The reason is that "the fastest kernel" is not a fixed thing. It depends on the GPU, the driver, the browser, the WebGPU features that device exposes, the data type, and the shape of the data you passed in this call. Two shaders that produce byte-identical output can differ wildly in speed on the same machine. Workgroup size, memory access pattern, vectorisation, and data type all move the number. So instead of guessing one winner, they ship the building blocks and let the loader assemble the right one on the spot.

This is the actual template for the vectorised addition path in ai.onnx.Add, fetched from the repository. The {% %} and {{ }} markers are the parts that get filled in or switched off before the shader is compiled:

{% if usesF16 %}
enable f16;
{% endif %}
{{ env.wgsl.resourceDeclarations }}

@compute @workgroup_size({{ tunables.WORKGROUP_SIZE }})
fn main(@builtin(global_invocation_id) gid: vec3<u32>, @builtin(num_workgroups) nwg: vec3<u32>) {
  // 2D-folded flat index: gid.y carries the high bits when the element count exceeds the
  // maxComputeWorkgroupsPerDimension limit (the dispatch caps x and spills the rest into y).
  let i = gid.x + gid.y * nwg.x * {{ tunables.WORKGROUP_SIZE }}u;
  if (i >= params.count) {
    return;
  }
  let av = a[i];
  let bv = b[i];
{% if scalar == "i32" or scalar == "u32" %}
  let r = av + bv;
{% if source.cDtype == "int8" %}
  c[i] = (r << vec4<u32>(24u)) >> vec4<u32>(24u);
{% elif source.cDtype == "uint8" %}
  c[i] = r & vec4<u32>(0xFFu);
{% else %}
  c[i] = r;
{% endif %}
{% elif scalar == "f16" %}
  c[i] = vec4<f16>(vec4<f32>(av) + vec4<f32>(bv));
{% else %}
  c[i] = av + bv;
{% endif %}
}

Read past the syntax and it is doing something simple: add two numbers, but write the addition differently for 8-bit integers, for 16-bit floats, and for everything else, and pick the workgroup size from a tunable rather than hard-coding it.

The decision of which template to use is data, not code. It lives in manifest.json as a list of variants with conditions. This is the first variant of ai.onnx.Add:

"variants": [
  {
    "id": "same_shape_vec4",
    "priority": 20,
    "when": [
      "sameShape(shapes.A, shapes.C)",
      "sameShape(shapes.B, shapes.C)",
      "numel(shapes.C) > 0",
      "numel(shapes.C) % 4 == 0",
      "f16Ok(dtypes.T)"
    ],
    "constants": {
      "scalar": "dtypes.T",
      "vectorScalar": "\"vec4<\" ~ dtypes.T ~ \">\"",
      "usesF16": "dtypes.T == \"f16\""
    },
    "passes": [ { "id": "main", "name": "Add.vec4",
      "source": { "shader": "binary-vec4.wgsl.jinja", ... } } ]
  },
  ...
]

In plain terms: if both inputs are the same shape as the output, and the element count divides evenly by four, and the data type is workable, then use the four-at-a-time vectorised shader, and prefer it (priority 20) over the more general fallbacks. The published Add kernel carries variants for equal shapes, vectorised broadcasting, scalar processing, and general broadcasting. ai.onnx.MatMul carries fourteen shader templates, including split-K reductions, tiled register variants, matrix-vector paths, and a subgroup-matrix path for devices that expose that feature.

You never see any of this. You call add(...) and the loader picks. But it is worth knowing it is there, because it explains why these are faster than a general-purpose implementation: a general implementation has to be correct for every case, so it takes the slow path for all of them.

4. What is actually inside a kernel repository

Every kernel is its own Hub repo with its own card, like a model. Five kinds of file matter:

  • manifest.json — the contract, and the source of truth. Inputs, outputs, attributes, allowed data types, how the output shape is derived, and the variant list shown above.
  • metadata.json — identifier, digests, provenance.
  • test.json — correctness cases, so any implementation can be checked against expected behaviour. For ai.onnx.Add this file is 31 KB.
  • bench.json — the benchmark and tuning cases used to evaluate the kernel.
  • *.wgsl.jinja — the parameterised shaders.
Non-obvious, and it will trip you up

Those files are not on the main branch. On main you get only README.md and .gitattributes. The real artifacts live on a branch named v1, under build/webgpu/. So the raw URL for the Add manifest is https://huggingface.co/kernels/webgpu-kernels/ai.onnx.Add/raw/v1/build/webgpu/manifest.json — note the /kernels/ path segment too, because a kernel is its own repository type on the Hub, not a model. The plain model-style URL returns an error.

The manifest is worth a look even if you never intend to write WGSL, because it is readable. It tells you that ai.onnx.Add is ONNX sinceVersion 14, accepts float32, float16, int32, uint32, int8 and uint8, that the output shape is broadcastShape(shapes.A, shapes.B), and that the default workgroup size is 256. You can understand what a kernel does without reading a shader.

The kernel card for ai.onnx.MatMul is equally direct. It documents that the kernel supports float16, float32, int32 and uint32; that all legal rank-1 to rank-4 combinations are implemented; that rank-5 works only when both inputs are rank 5; and that some variants need the subgroup-matrix, shader-f16 or subgroups device features — which are per-route capabilities, not requirements for the whole package.

5. Using one: the whole API in five minutes

Install it. Note the @preview tag — this is an early preview, and the published version at the time of writing is 0.0.1-preview.1:

npm install @huggingface/kernels@preview

You need a browser with WebGPU. Check for it with "gpu" in navigator. Availability depends on browser, operating system, GPU and driver, so treat it as a feature you detect, not a guarantee.

The pattern is always the same. Ask for a kernel by repo ID and contract version. You get back an async function. Call it with named inputs, each one a typed array plus a shape:

import { getKernel } from "@huggingface/kernels";

const add = await getKernel("webgpu-kernels/ai.onnx.Add", { version: 1 });

const { c } = await add({
  a: { data: new Float32Array([1, 2, 3, 4, 5, 6]), shape: [2, 3] },
  b: { data: new Float32Array([10, 20, 30]),       shape: [3]    },
});

The second input is broadcast across the first dimension, so c comes back with shape [2, 3]. You did not tell it that. The loader read the output shape rule out of the manifest, worked out the result shape and data type from your inputs, and allocated the output for you.

Matrix multiplication is the same call with a different repo ID:

const kernel = await getKernel("webgpu-kernels/ai.onnx.MatMul", { version: 1 });
const { y } = await kernel({
  a: { data: aData, shape: [3, 5] },
  b: { data: bData, shape: [5, 4] },
});
console.log(y.data, y.shape, y.dtype);

Adding six floats on a GPU is deliberately silly — the round trip to the device costs far more than the arithmetic. The point of the tiny example is that the call shape does not change when you move to the operations where the GPU genuinely wins.

The four options that matter

version: 1 selects version 1 of the published kernel contract. It is not an ONNX opset, not an operator's since_version, and not a model revision — keeping those separate is what lets your JavaScript stay stable while the shaders underneath get rewritten. Practically, version: 1 follows the repository's v1 branch, and that branch moves as fixes land.

revision takes a 40-character commit hash instead. Use it when you want bytes that can never change under you — a reproducible build, a paper, anything you will be asked to explain in six months.

{ output: "gpu" } keeps the result on the device instead of copying it back to JavaScript. This is the one that turns a toy into a pipeline. Chained operations — multiply, then add a bias, then normalise, then softmax — should never round-trip through CPU memory between steps. You own those GPU buffers, and you release them with destroy().

{ trustRemoteCode: true } is required to load a kernel from any publisher other than the webgpu-kernels organisation. The reasoning is blunt and correct: a kernel is code that runs on your GPU. Loading someone else's is opt-in, deliberately.

Data types

You pass the natural typed array — Float32Array, Uint8Array, Float16Array, and so on — and the library widens it to the right WebGPU storage form. Results come back the same way, with one wrinkle worth remembering: float16 comes back as a Float16Array where the browser provides one, and otherwise as raw binary16 words packed into a Uint16Array. If you support float16, handle both.

6. How fast are they, honestly

Hugging Face compared their collection against ONNX Runtime Web (build 1.30.0-dev.20260826-b1f76d586a) on an Apple M4 GPU. They started with 1,756 test cases across all 207 operations, and kept the 809 cases where both sides produced matching outputs and reliable timings.

Across those 809 comparisons: 2.57x faster by geometric mean, 1.90x faster at the median, with 629 wins, 176 losses and 4 ties. Four familiar operations:

OperationCasesHF WebGPU kernelORT WebGPUSpeedup
Add50.064 ms0.227 ms3.52x
MatMul290.115 ms0.131 ms1.14x
Softmax120.114 ms0.240 ms2.11x
LayerNormalization60.061 ms0.135 ms2.22x

Two outliers are worth naming because they show what a specialised kernel does when a general one falls off a cliff. A bilinear Einsum case — the contraction i,ij,j at size 4096 — ran in 0.136 ms against 1,396 ms for ORT WebGPU. That is more than 10,000x. A row-wise CumSum over a [256, 4096] tensor ran in 0.016 ms against 4.784 ms, about 301x.

Read the caveats, they are load-bearing

These are not the speedups to expect everywhere. They are the cases where a general implementation hit a pathological slow path, and Hugging Face say so themselves.

Four more limits, all stated in the blog post. The timings cover work done on the GPU only — loading kernels, creating sessions, uploading inputs, compiling shaders and reading results back are all excluded. Very short workloads are hard to measure and small cases can sit entirely in GPU cache. These are individual operations, not whole models, so you cannot multiply them out into an end-to-end model speedup. And it is one device: an M4. Your Windows machine will produce a different table.

Hugging Face also say they are working with the ONNX Runtime team to upstream the improvements, which means some of this gap is expected to close from the other side.

A different kind of number comes from the launch video's demo. A 1,024 × 1,024 grid — over a million cells — with 128 waves crossing it, where every cell's RGBA colour comes out of a single matrix multiplication, runs at about 60 frames per second. That 60 is a ceiling imposed by requestAnimationFrame, not by the GPU; the presenter estimates the maths itself could sustain around 400 fps. The same calculation in plain JavaScript drops to roughly 6.7 fps.

7. What the 207 kernels cover

I pulled the full list from the Hub API. It splits into two families:

  • 175 ai.onnx.* kernels — the standard ONNX operator set. Everything from Abs and Add through Conv, Gemm, MatMul, Resize, TopK, the whole Reduce* family, DFT, STFT, GridSample, NonMaxSuppression, and the quantisation operators QuantizeLinear, DequantizeLinear, DynamicQuantizeLinear, MatMulInteger and QLinearMatMul.
  • 32 com.microsoft.* kernels — the ONNX Runtime contributed operators, which is where the fused and LLM-specific work lives.

If your interest is language models specifically, the ones to know are ai.onnx.Attention, com.microsoft.MultiHeadAttention, com.microsoft.GroupQueryAttention, com.microsoft.PagedAttention, com.microsoft.SparseAttention, ai.onnx.RotaryEmbedding and its Gemma and multimodal variants, ai.onnx.RMSNormalization, ai.onnx.SwiGLU, com.microsoft.MoE and com.microsoft.QMoE, and the quantised matmul family com.microsoft.MatMulNBits, MatMulNBitsMlp, MatMulNBitsQkv and MatMulBnb4. That is not a random assortment. That is the ingredient list for running a modern quantised transformer in a browser tab.

The kernels also appear on the Hub's general Kernels page, alongside kernels for CUDA, ROCm and Metal, filterable and sortable like any other Hub artifact.

8. Fleet, and why your GPU is worth something to them

Fleet is a web page that loads the kernels from the Hub, runs the correctness and benchmark cases on whatever GPU you happen to have, and scores it. You see how your hardware performs. With your consent, the run also contributes evidence back privately.

The honest reason they built it is stated plainly in the video: the team optimised these kernels on the devices they had — their own machines, "devices we found in our homes". There are thousands of GPU, driver and browser combinations in the world, and edge cases they cannot have anticipated. Every submitted run can reveal an incorrect result, a pathologically slow path, or a variant-selection rule that picks badly on some specific chip.

Concretely: a Windows machine with a discrete or integrated GPU that is not an Apple M-series part is exactly the kind of data point their benchmark table does not have. Opening the page and pressing run is a two-minute, zero-code contribution to an open-source project.

9. Projects worth building with this

Now the useful part. Below are five directions, ordered roughly from "works today, small effort" to "ambitious". I have tried to be honest about which are real and which are still waiting on missing pieces.

a. Heavy visual or numerical work in a page that currently crawls

This is the most immediately usable idea, and it has nothing to do with AI. If you have any web page doing large amounts of arithmetic per frame — a simulation, a generative animation, a large data grid, an image filter, a spectrogram — one kernel can replace the loop.

The wave demo is the proof. Over a million pixels, coloured every frame, using exactly one kernel: ai.onnx.MatMul. Prepare the data, do one matrix multiply, get RGBA values for the whole grid. 60 fps against about 6.7 fps for the same maths in plain JavaScript. There is no model, no inference, no ONNX file involved — just the observation that a matrix multiply is a very general hammer and the GPU is very good at it.

Signal processing has an easy entry too: ai.onnx.DFT and ai.onnx.STFT are in the collection, so audio analysis in the browser is a kernel call rather than a library.

b. Building blocks for private, local inference

The video's second demo implements a transformer attention mechanism in roughly 20 lines of JavaScript, using four kernels: MatMul, Softmax, Add and LayerNormalization. It loads real weights — the presenter says "tiny bird", which is almost certainly TinyBERT — and draws a heat map where each row shows how strongly one token attends to another. Bright cell, strong link.

That is a genuinely good learning artifact and a genuinely good demo: it shows attention working, on real weights, on your own GPU, with nothing leaving the machine. If you want a piece to explain how transformers work to someone, twenty lines they can read beats a diagram.

The gap you need to know about

There is no model runner in this release. You cannot point @huggingface/kernels at a .onnx file and get a working model. The blog post is explicit that connecting these kernels to "higher-level model tooling" is future work — this is the bottom layer, published first, on purpose.

If you want to run a whole model in a browser today, the answer is still Transformers.js, which uses ONNX Runtime Web. These kernels sit underneath that layer, and Hugging Face are upstreaming improvements to ONNX Runtime so the benefit reaches it eventually. Build with kernels when you want a specific computation; use Transformers.js when you want a model.

c. A small tool that offloads one expensive computation to the browser GPU

The interesting property of this library for tooling work is that it removes the setup cost of GPU compute. There is no CUDA install, no driver version, no Python environment, no build step — a web page, a browser with WebGPU, and an npm package. On Windows that matters more than it does elsewhere, because the usual local-GPU path involves the whole CUDA toolchain.

Concrete shapes this could take: embedding similarity search over a few thousand vectors, done as one MatMul plus a TopK, in a page. A clustering or dimensionality-reduction step in a data-inspection tool. A cosine-similarity matrix over documents. Any of these are a handful of kernel calls and, with { output: "gpu" }, they chain without leaving the device.

Given that you build on the Claude Code platform, the natural version of this is a self-contained HTML artifact that does real GPU compute — a page that loads a kernel from the Hub, runs a heavy calculation locally on the viewer's own hardware, and shows the result. No server, no API key, no data leaving the browser. That constraint set is unusual and it is exactly what this library gives you.

d. Contribute without writing code

Run Fleet on every machine you have access to and submit the results. It costs two minutes, and it is the single most useful thing a person with unusual hardware can do for this project right now. Their benchmark table is one M4. It should not be.

e. Read them as reference implementations

Hugging Face explicitly offer the kernels as reference material for people writing their own WebGPU code or building their own runtimes. If you have ever wanted to understand how a fast matrix multiply is actually structured, ai.onnx.MatMul ships fourteen shader templates with names that describe the strategy — tiled, register-tiled, split-K, matrix-vector, subgroup-matrix — and a manifest that spells out the conditions under which each one is chosen. That is a curriculum, not just a codebase, and it is Apache-2.0.

10. This laptop, measured

Everything above this point is other people's numbers. This section is measured on the machine the report was written on, on 4 September 2026.

The hardware

  • HP Victus 15-fa0xxx — Intel Core i5-12450H, 8 cores, 31.7 GB RAM, Windows 11 Home
  • NVIDIA GeForce RTX 3050 Laptop GPU, 4 GB, driver 32.0.15.9282
  • Intel UHD Graphics, architecture gen-12lp, driver 32.0.101.5542
  • Chrome 152, WebGPU available

The method

A single local HTML page, served over localhost, importing the library straight from a CDN. Correctness first: ai.onnx.Relu on [-1, 0, 2, -3] returned [0, 0, 2, 0]. Then ai.onnx.MatMul on square float32 matrices, with warm-up runs discarded and the median reported.

Useful finding — no build step needed

The package imports directly as an ES module from jsDelivr. There is no npm install, no bundler, and no build tooling. One HTML file is a complete, working project:

const m = await import("https://cdn.jsdelivr.net/npm/@huggingface/kernels@preview/+esm");
const mm = await m.getKernel("webgpu-kernels/ai.onnx.MatMul", { version: 1 });

The import fails on pages with a restrictive Content-Security-Policy — it was blocked on the Fleet page and worked immediately from localhost.

Chrome does not pick the fast GPU by itself

On the first run, all three power preferences — high-performance, low-power and the default — returned the same adapter: intel / gen-12lp. The RTX 3050 was never touched. This is not a bug in the library. Chrome binds one adapter when its GPU process starts, so powerPreference cannot switch cards afterwards. The fix is a Windows setting, and it needs a full Chrome restart:

The fix is a Windows per-application graphics preference. Nobody remembers this path, so here it is in full. It is written for Windows 11 build 26200 (September 2026); older builds differ, and that difference is noted at step 6.

Click path — point Chrome at the discrete GPU
  1. Press Win + I to open Settings.
  2. In the left sidebar, select System.
  3. Select Display.
  4. Scroll to the bottom of the Display page. Under Related settings, select Graphics. The breadcrumb should now read System > Display > Graphics.
  5. Find Google Chrome in the app list. If it is not listed: select Add desktop app, then Browse, then choose C:\Program Files\Google\Chrome\Application\chrome.exe.
  6. Click the Google Chrome row to expand it. You will see a GPU preference line with a dropdown that reads Let Windows decide.
    On older Windows 11 and Windows 10 builds there is no inline dropdown. Instead the row shows an Options button; click it, choose the preference in the dialog, then click Save.
  7. Open the dropdown. It lists Let Windows decide, Power saving and High performance. Power saving is the integrated Intel chip. High performance is the NVIDIA card.
  8. Select High performance. The current build applies it immediately — there is no Save button.
  9. Quit Chrome completely. Closing every window is not enough: check the notification area (the tray, next to the clock) for a Chrome icon and quit that too. The preference is only read when the browser's GPU process starts.
  10. Start Chrome again.

The setting is stored per executable in the registry, under HKCU\Software\Microsoft\DirectX\UserGpuPreferences, as one value per application path with the data GpuPreference=2 for high performance (1 is power saving). Reading that key is the quickest way to confirm the preference exists without opening Settings.

To verify the browser actually changed cards, open any page over https or localhost, open DevTools with F12, and run this in the Console:

(await navigator.gpu.requestAdapter({ powerPreference: "high-performance" })).info

Before the change it reported vendor: "intel", architecture: "gen-12lp". After the change and a restart it reported vendor: "nvidia", architecture: "ampere". If it still says intel, Chrome did not fully quit — return to step 9.

Result 1: the discrete GPU barely helped

Adapter1024×1024 MatMul, median
Intel UHD (gen-12lp)36.4 ms
RTX 3050 (ampere)33.7 ms

Identical script, identical method. An 8% gain from a discrete GPU is not credible, so the benchmark was wrong, not the hardware.

Result 2: the copy was the cost, not the maths

Splitting the round trip from the compute, on the RTX 3050:

MatrixFull round tripResult kept on GPUBytes moved per call
1024×102426.6 ms — 81 GFLOP/s9.28 ms — 231 GFLOP/s12 MB
2048×204868.8 ms — 250 GFLOP/s38.2 ms — 450 GFLOP/s48 MB

Adding { output: "gpu" } made the same work 2.9x faster at 1024 and 1.8x faster at 2048. The arithmetic did not change. The only difference is that the answer stopped being copied back into JavaScript.

That also explains why the discrete card looked flat. A discrete GPU sits behind the PCIe bus, so every input crosses it on the way in and every read-back crosses it on the way out. Integrated graphics share memory with the CPU and pay far less for the same copy. The RTX 3050 wins the arithmetic and hands part of the win back on transport.

The rule this produces

Chain kernels with { output: "gpu" } and read back exactly once, at the end. A pipeline that returns to JavaScript between every step spends most of its time copying. This is true on this laptop, and more true on any discrete card.

It re-ranks the project ideas above. The wave grid works well because it computes a million pixels from small inputs. Embedding similarity works well because the vectors upload once and stay. Any design that pushes a large array in and pulls a large array out every frame will disappoint you.

Result 3: one ceiling stays in place

Both adapters report shader-f16 and subgroups. Neither reports subgroup-matrix — Chrome 152 does not expose it here. So MatMul's matmul-subgroup-matrix-ext.wgsl.jinja variant is never selected on this machine, the tiled variants run instead, and the tensor cores stay idle. The 450 GFLOP/s figure sits well below this card's float32 peak, and that is the reason.

The 4 GB of video memory is not a limit at this scale. It only constrains whole models, which this library does not run.

How to read these numbers

They are wall-clock times, not the GPU-only timings used in the blog's M4 table, so the two are not comparable. Even the "kept on GPU" column still re-uploads both inputs on every iteration, so the true compute time is lower than shown. The first timed call after a cold start took 201 ms against a 33.7 ms median — warm up before measuring anything. And this is one laptop, which is precisely the argument for running Fleet on it.

11. How these tests were run

Section 10 is only worth anything if you can repeat it. The harness is one self-contained file, bench.html, sitting next to this report. It needs no npm, no bundler, and no dependencies beyond a browser.

Running it

Reproduce in three commands
  1. cd webgpu-projects
  2. python -m http.server 8793
  3. Open http://localhost:8793/bench.html and wait about 20 seconds.

Results render on the page and are also left in window.__result, so you can read them from the DevTools console or from an automation tool. Stop the server with Ctrl + C.

A local server is required. Opening the file directly with file:// fails, because the CDN module import is blocked from that origin. localhost counts as a secure context, so WebGPU works there without a certificate.

What the harness measures, and why it is built that way

Step 0 — environment. It records the adapter's vendor and architecture, and then checks three features by name: shader-f16, subgroups, and subgroup-matrix. The last one is the interesting one, because its absence is what keeps the fastest MatMul variant from ever being selected.

Step 1 — load. It tries jsDelivr first and falls back to esm.sh, recording which one worked. Any import failure is kept in the output rather than thrown away, because a page's Content-Security-Policy is the usual cause and the message says so.

Step 2 — correctness before speed. It runs ai.onnx.Relu on [-1, 0, 2, -3] and compares the result against [0, 0, 2, 0], reporting a pass boolean. A fast wrong answer is not a result. This check runs first so a broken load cannot masquerade as a slow one.

Step 3 — speed, measured twice. For each size, ai.onnx.MatMul is timed two ways. The first is the ordinary call: upload both inputs, compute, copy the answer back into JavaScript. The second passes { output: "gpu" } so the answer stays on the device. The difference between the two columns is the entire argument of section 10.

Three details in that step matter. Three warm-up calls are discarded before timing, because the first call after a cold start ran about six times the median. Fifteen timed runs are sorted and the median taken, not the mean, so one scheduling hiccup cannot move the number. And the GPU-resident variant has no per-call read-back to synchronise against, so it times the whole batch of fifteen and then issues one ordinary reading call to force the queue to drain, before dividing. Timing GPU work without a synchronisation point measures how fast you can submit, not how fast the work finishes — that is the easiest way to produce a fake result here.

The held buffers are released with destroy(). With { output: "gpu" } you own them; fifteen undestroyed 4 MB buffers per size would leak.

Step 4 — the plain-JavaScript reference. A 128×128 tile is timed with three nested loops, then cubed up to 1024. It is labelled an estimate inside the output itself, because the small tile fits in cache and real JavaScript at full size would be worse. It is there for scale, not for a ratio you should quote.

What was measured outside the harness

Two things in section 10 did not come from bench.html. The GPU inventory and driver versions came from Get-CimInstance Win32_VideoController in PowerShell. The finding that Chrome ignores powerPreference came from calling requestAdapter three times in one page — with high-performance, with low-power, and with no preference — and observing that all three returned the same Intel adapter.

Reproducibility, honestly stated

The suite was run twice on the RTX 3050, in separate browser sessions. Both runs agree on the conclusion and differ on the digits:

MeasurementFirst runSecond run
1024 round trip26.6 ms25.8 ms
1024 result on GPU9.28 ms9.63 ms
2048 round trip68.8 ms75.8 ms
2048 result on GPU38.2 ms36.4 ms

That is roughly 10% of run-to-run variation on a laptop with thermal limits and other software running. The 2.1x to 2.9x advantage of keeping results on the GPU is far larger than that spread, so it is a real effect. A 10% difference between two other numbers on this page would not be.

Section 10's two-adapter comparison (36.4 ms against 33.7 ms) is a single run of each. Given the variance above, treat that 8% gap as "no measurable difference" rather than as a small win for the discrete card — which is exactly why the second, split measurement was needed.

Changing it

To test other kernels, change the repository ID in getKernel and the input names to match that kernel's card — the bind keys are listed in its Inputs table. To test other sizes, edit the [1024, 2048] array. To tighten the numbers, raise RUNS from 15. To measure a different GPU, change the Windows graphics preference using the click path in section 10 and restart Chrome; the harness reports which adapter it actually got, so a mislabelled result is not possible.

12. Limits and gaps you should know before you start

  • It is an early preview. The npm README says so directly: the API may still change, and kernel coverage is growing. The published version is 0.0.1-preview.1, installed with the @preview tag. Do not build something load-bearing on it without pinning a revision.
  • WebGPU is not everywhere. Availability depends on browser, operating system, GPU and driver. Detect it with "gpu" in navigator and have a fallback path.
  • Some fast paths need optional device features. The MatMul card names subgroup-matrix, shader-f16 and subgroups. If your device lacks them, you get a correct answer from a slower variant, not an error — but you also do not get the headline numbers.
  • Coverage inside a kernel is not total. MatMul implements all legal rank-1 to rank-4 combinations, but rank-5 only when both inputs are rank 5; mixed-rank cases involving a rank-5 operand are not yet implemented, and neither are higher ranks or the remaining ONNX types. Read the kernel card, not just the operator name.
  • No model runner yet, as covered above.
  • The benchmark is one machine. Treat 2.57x as evidence that the approach works, not as a number you can quote for your own hardware until you have run Fleet on it.
