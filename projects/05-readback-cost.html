The science

This page is not measuring the GPU. It is measuring the cost of asking the GPU a question and waiting for the answer.

A matrix multiply of two N×N matrices does about 2N3 arithmetic operations and moves about 4N2 bytes for each matrix it has to transfer. The ratio of the two is the arithmetic intensity, 2N3 / (8N2) = N/4 operations per byte — 64 at N = 256. By that measure the transfers ought to be free at large N, and the two curves ought to converge. They do not.

The reason is that a readback is not only bytes, it is a synchronisation. Mapping a buffer forces the queue to drain: the CPU must wait for every dispatch to retire before it can read, and the GPU then sits idle while JavaScript copies the array and issues the next call. Nothing overlaps. The eight-call chain pays this seven times, and each round trip costs a fixed latency that does not shrink as N grows. So the gap is dominated by a term proportional to the number of readbacks, not their size — which is why the measured ratio settles into a band of 3.0 to 4.6× instead of closing.

The rule that follows is the practical one for any GPU pipeline: batch work into long chains that stay resident, and cross the boundary once. The last column counts the bytes never copied, 7 × 2 × 4N2, which is the visible half of a cost whose larger half is the waiting.

Readback means the result buffer is mapped and copied to a typed array after every call, then uploaded again for the next one. On-card means { output: "gpu" }, so the buffer is handed straight to the next call. The last column is the bytes the on-card mode never copies. To keep the values finite over eight multiplies, B is scaled by 1/N. Run-to-run variance on this laptop is about 10%, so read a gap smaller than that as noise. Chrome picks one GPU at startup, so this measures whichever adapter Chrome holds now.
